# Recovery after a wrong tool action

The desktop server now saves the original bytes and mode of every local `write_file` or `edit_file` target before atomic replacement. The private receipt lives in that session's output directory under `recovery/`; the change event and model-visible tool result include its recovery ID. A later `restore_file_change` call presents the reverse diff for fresh approval. It restores the prior file or removes a file that did not exist before the write.

Restoration is conditional: the target must have exactly the recorded post-write content and mode when checked. A different or redirected target is refused so recovery does not silently erase different work. The receipt is consumed after a successful restore. This is an explicit user/agent action, not automatic detection by the same judge. The check and replacement are serialized within one agent process; external writers can still race them, and an identical later rewrite is indistinguishable from the original result. Sessions retain their own receipts; switching to another session does not transfer them. Receipt files contain the original source text and must stay private; session deletion removes the recovery material.

This only covers built-in local UTF-8 file writes/edits. CLI mode and injected file backends do not advertise the restore tool. Undoing a newly created file leaves its parent directories in place. Shell commands, custom mutations, network calls and Git pushes can have effects outside the workspace; a file receipt does not reverse them. Read-only commands may still violate a user's “do not run” request even when there is no file change to undo. Existing approvals and risk checks remain necessary.

The frozen 144-row synthetic boundary diagnostic has 11 false allows for the new format checkpoint: seven `write_file`/`edit_file` proposals, three `command -v java javac` calls, and one compound `javac -version; git push origin main` proposal. These are repeated variants of constructed cases, not 11 independent incidents. The seven file proposals would be eligible for conditional restoration **if** a local write actually occurred and its result remained unchanged. The three lookups have no expected workspace file mutation; the compound command has an external side effect that cannot be covered by this mechanism. This is a coverage classification of proposed tools, not an observed recovery success rate. Real-task recovery needs a separate end-to-end evaluation.
